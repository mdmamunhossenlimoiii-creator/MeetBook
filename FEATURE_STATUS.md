| Bot identities and behavior | 23 built-in fictional bot profiles have role-specific emoji markers; UI keeps the AI Bot disclosure. The first three bots (bot_01–bot_03) use Gemini with template fallback and up to six recent messages as short-term context. An opt-in, per-user/per-bot long-term memory summary is implemented for those three bots only; raw transcripts are not stored. Missing or permission-denied optional memory documents are skipped without aborting a chat reply. Gemini output is checked for obvious first-person human/real-person identity, credential, and personal-experience claims; unsafe output falls back to the role-safe template, while strict live mode fails closed. This conservative pattern filter cannot detect every possible claim. Remaining bots use keyword/template behavior and do not yet have Gemini memory summarization. Post repetition guard: the Runner stores SHA-256 fingerprints of normalized post text (up to 8,000) and compares the last 100 normalized texts across bots assigned to that Runner. Repeated generated output falls back to a fresh role template or is skipped; manual bot workflows share a non-cancelling concurrency group. This history is scoped to the dedicated Runner account. | Memory is off by default. Users can opt in, see the disclosure, inspect/delete individual summaries, clear all saved summaries, or disable memory. Account deletion also purges owned bot memories. Summaries are bounded to 1,200 characters and built only from user-authored messages. Email/phone patterns are redacted, and messages or summaries matching common credential, financial, ID, precise-address/location, health, political/religious, or sexuality/identity terms are excluded by a conservative heuristic. This cannot guarantee detection of every sensitive detail; memory remains opt-in and off by default. Real Gemini API memory summarization has not been verified. |
| Bot Runner security | Runner is restricted by an explicit 23-ID bot allowlist and global kill switch. ## Release decision

**Not release-ready.** PR #19 is the clean, current-main integration candidate and GitHub currently reports it mergeable, but it remains draft. PR #16 also remains draft and GitHub reports it non-mergeable. No PR has been merged or published in this work.

Owner-only gates remain:
- Verify the existing-account public profile/directory/consent projection migration against actual MeetBook accounts.
- Confirm Firebase project meetbook-65d30, enabled Auth providers, the actual Pages hostname in authorized domains, first Super Admin, and the App Check decision. No production Rules publication has been verified.
- Ensure eligible users' users/{uid} documents have banned explicitly set to Boolean false and suspendedUntil is absent, null, or expired; missing/malformed status intentionally blocks image uploads.
- Deploy the Cloudflare image Worker and SQLite Durable Object migration; configure Cloudinary API key/secret as Worker secrets; verify the actual Pages origin; set imageUploadEndpoint; configure outer abuse/rate controls; and test real profile/post/story/message uploads.
- Run isolated staging E2E for Runner authentication, one user-initiated reply, consent-gated public engagement, and real Gemini behavior.
- Verify GitHub Pages/public URL behavior and investigate the historical Run #30 failure.

No credentials or secrets are requested or added here. No Firebase or production settings were changed, no live bot workflow was dispatched, and no merge, publish, or deployment was performed. MySocial remains separate and untouched.
