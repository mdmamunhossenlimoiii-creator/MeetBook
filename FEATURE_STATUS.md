| Profiles and privacy | Full `publicProfiles/{uid}` metadata is restricted by Firestore Rules to the owner, staff and bots; it is visible to everyone when `profileVisibility == everyone`, or to friends when `profileVisibility == friends`. A separate `publicDirectory/{uid}` exposes only display name/name search and minimal account markers for discovery; it excludes bio, photo, cover and settings. | Global/Friends search uses the minimal directory. This intentionally leaves a user's display name and minimal account markers discoverable even when detailed profile visibility is friends; the owner must confirm that this discovery behavior is acceptable. A private profile route shows only the directory name and friend-request controls when detailed metadata is denied. Profile visibility and directory projections are bound to canonical `users/{uid}` fields using `getAfter`. Public posts remain governed by each post's own audience and may still appear in feeds. The safe admin backfill creates/updates only the minimal `publicDirectory` projection and missing bot profiles. Human detailed `publicProfiles` and `botEngagement` consent projections remain owner-created on the next successful sign-in. Sign-in and owner profile/settings writes replace exact allowlisted projection documents to remove stale legacy fields. The Runner can get one target user's minimal `botEngagement` projection but cannot list the collection; this is a per-document access boundary, not an anonymity guarantee for a UID already known to an authorized Runner. Full existing-account migration verification is still required before release. |

| Bot identities and behavior | 23 built-in fictional bot profiles have role-specific emoji markers; UI keeps the AI Bot disclosure. The first three bots (`bot_01`–`bot_03`) use Gemini with template fallback and up to six recent messages as short-term context. An opt-in, per-user/per-bot long-term memory summary is implemented for those three bots only; raw transcripts are not stored. Missing or permission-denied optional memory documents are skipped without aborting a chat reply. Dry runs do not read persisted memory documents, even when memory consent is enabled. Gemini output is checked for common English and Bengali first-person human/real-person identity, credential, and personal-experience claims; unsafe output falls back to the role-safe template, while strict live mode fails closed. The Bengali guard also catches English proper-name claims after a Bengali first-person prefix. This conservative pattern filter cannot detect every possible claim. Remaining bots use keyword/template behavior and do not yet have Gemini memory summarization. Post repetition guard: the Runner stores SHA-256 fingerprints of normalized post text (up to 4,000) and compares the last 100 normalized texts across bots assigned to that Runner. Repeated generated output falls back to a fresh role template or is skipped; manual bot workflows share a non-cancelling concurrency group. This history is scoped to the dedicated Runner account. | Memory is off by default. Users can opt in, see the disclosure, inspect/delete individual summaries, clear all saved summaries, or disable memory. Account deletion also purges owned bot memories. Summaries are bounded to 1,200 characters and built only from user-authored messages. Email/phone patterns are redacted, and messages or summaries matching common credential, financial, ID, precise-address/location, health, political/religious, or sexuality/identity terms are excluded by a conservative heuristic. This cannot guarantee detection of every sensitive detail; memory remains opt-in and off by default. Real Gemini API memory summarization has not been verified. |
| Bot Runner security | Runner is restricted by an explicit 23-ID bot allowlist and global kill switch. The canonical global settings document is `settings/overall`, matching the existing Firebase document; missing or non-Boolean `botsEnabled` and Runner `enabled` values fail closed; user consent, public-post, private-chat, AI-label, blocked/suspended-account gates for public engagement, private chat history, replies and memory are enforced in Rules. Version-2 inbox items store routing metadata and a message ID only; the sender can get their own metadata and the assigned active Runner can list only version-2 metadata. Runner consent checks use direct per-user gets; Firestore Rules deny collection enumeration. Legacy unversioned items are excluded from Runner queries. The Runner fetches the actual message only after private-chat eligibility passes; staff cannot read inbox metadata or private chat bodies. Admins may create/delete bots and toggle only the `active` Boolean; Firestore Rules deny Admin identity edits, publishing and commenting. | Durable Firestore transaction-backed quotas are implemented and covered by CI/emulator tests: 12 actions per bot per rolling 24 hours; 15 replies per user per bot per rolling 24 hours with a 60-second cooldown; and 20 user-to-bot inbox messages per rolling 24 hours with a 10-second cooldown. Isolated live staging verification is still required. |

## Release decision

**Not release-ready.** PR #16 is the original feature branch PR and remains draft/non-mergeable because its history diverges from current main (215 commits ahead, 1 behind). PR #19 remains a separate draft integration candidate, but it is not synchronized with the latest feature-branch Worker and documentation changes; its latest CI state is not currently verified. No PR has been merged or published in this work.

Owner-only gates remain:
- Verify the existing-account public profile/directory/consent projection migration against actual MeetBook accounts. Confirm that exposing display names and minimal account markers in publicDirectory is acceptable even for profiles whose detailed visibility is friends.
- Confirm that the existing Firebase project `meetbook-65d30` is dedicated to MeetBook and not shared with MySocial; create a separate project only if this check fails. Verify enabled Auth providers, the actual Pages hostname in authorized domains, first Super Admin, and the App Check decision. No production Rules publication has been verified.
- Ensure eligible users' `users/{uid}` documents have `banned` explicitly set to Boolean false and `suspendedUntil` is absent, null, or expired; missing/malformed status intentionally blocks image uploads. Human profiles may omit `isBot`, but a present malformed value is rejected and bot profiles cannot upload.
- Decide whether profile photos/covers and other uploads are intentionally public. The current Cloudinary `image/upload` URLs are publicly deliverable; Firestore profile visibility does not protect the image bytes. If private media is required, signed/authenticated delivery must be implemented before upload activation. Deploy the Cloudflare image Worker and SQLite Durable Object migration; configure Cloudinary API key/secret as Worker secrets; verify the actual Pages origin; set `imageUploadEndpoint`; configure outer abuse/rate controls; and test real profile/post/story/message uploads.
- Run isolated staging E2E for Runner authentication, one user-initiated reply, consent-gated public engagement, and real Gemini behavior.
- Verify GitHub Pages/public URL behavior and investigate the historical Run #30 failure.

No credentials or secrets are requested or added here. No Firebase or production settings were changed, no live bot workflow was dispatched, and no merge, publish, or deployment was performed. MySocial remains separate and untouched.
